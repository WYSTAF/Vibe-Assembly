## Part 1 — What Vibe Assembly is

### The one-sentence version

A multi-agent workspace template that lets you build large software projects on
**free AI tiers** by never putting more than one job in a single AI chat.

### The problem it solves

Coding with an LLM, you keep one chat open. It works. Then it doesn't:

- The context window fills. On free tiers (OpenRouter, Cloudflare Workers AI,
  Gemini free), that happens fast.
- Past that point the model starts forgetting your architecture.
- Then it hallucinates APIs that don't exist, and breaks working code.
- Then you have a chat full of confused reasoning and no way to resume.

This is a **context problem**, not a model problem. A better model moves the
wall; it doesn't remove it.

### The solution: five employees who never share a chat

The fix is to stop treating the AI as one worker and start treating it as five
with separate contexts, communicating **only through files** in `.ai/`.

| Mode | Slug | Role | Owns |
|---|---|---|---|
| 👑 Boss | `1-boss` | Architect + PM. Writes ticket blueprints. | All `.ai/` planning state. **Never production code.** |
| 💬 Chat | `2-chat` | Product brainstorming. Brainstorm in any language; durable artifacts stay English. | Conversation only. |
| 💻 Code | `3-code` | Implements only what Boss authorized. | Exactly one pointed ticket, inside `files_allowed`. |
| 🐞 Debug | `4-debug` | Surgical fixes when tests/builds fail. | Sole owner of `known_bugs.md`. |
| 📣 Hermes | `5-hermes` | Docs & release notes, from disk evidence only. | Root `*.md`, `docs/`, `plans/`, `changelog.md`. Never production code, never `active_task.md`. |

Because each mode starts with a fresh context, **none of them ever hits the
limit.** The limit moves from "chat length" to "ticket size", and tickets are
small by design.

### The `.ai/` contract — the actual mechanism

The modes never talk to each other. They read and write these files:

| File | Purpose |
|---|---|
| `active_task.md` | **The heart.** Wave, Active Ticket pointer, Queue table, per-ticket detail. |
| `current_state.md` | Operational state, blockers, resume anchor. |
| `known_bugs.md` | Forensic anomaly log (`KB-NNN`). |
| `decisions.md` | Architectural decision log (`ADR-NNN`). |
| `progress.md` | Wave history. |
| `ticket_contract.md` | The spec the above must satisfy. |
| `model_knowledge.json` | Model classes + per-mode model requirements. |
| `model_combo.txt` | Your router model list (one per line). You create it by renaming `model_combo.example.txt`. **Not currently gitignored** — see Recommendation 7. |

#### The ticket contract

`active_task.md` holds a queue of tickets. Each ticket has:

- `id`, `title`, `status`, `order`, `depends_on`, `effort`
- `files_allowed` — a hard allowlist, the only editable paths
- `context_inline` — durable facts, never "as discussed"
- `steps` — 3–12 steps, each ending with a `Verify:` command + expected result
- `done_when` — machine-checkable
- `stop_when` — escalation trigger
- `relay_notes` — append-only evidence, starts empty

**Exactly one Active Ticket pointer** exists, and it is the *sole* execution
authority. Code does not infer work from the queue. This is
[ADR-007](.ai/decisions.md) and it is the single most important design decision
in the system: it removes the ambiguity of "which row do I run?" that would
otherwise make interrupted sessions unresolvable.

#### The relay mechanism — how sessions survive death

After each step, Code appends one bullet to `relay_notes` containing the step
number, changed paths, exact command, and exit code. A step counts as **verified**
only when a *single* note both:

1. references that exact step number (word-boundary matched), **and**
2. carries success evidence (`PASS` or `exit 0`).

Both conditions must appear in the *same* note. This is what makes it impossible
for one `PASS` to verify every step, and it is enforced identically in two
independent implementations (see Part 2).

The resume point is simply **the first unverified step**.

#### Fail-closed validation

Nine contract violations are detected, and any of them halts execution rather
than guessing: duplicate queue IDs, missing pointer, `none` with work remaining,
wrong row count for the pointer, non-`pending`/`in_progress` status, Meta/Queue
status mismatch, missing dependency, unfinished dependency.

### Model allocation

`model_knowledge.json` defines 5 capability **classes** (not benchmark scores):

| Class | For |
|---|---|
| `reasoner` | Deliberate multi-step thinking; root-cause diagnosis. |
| `coder` | Instruction-tuned for code diffs; allowlist execution. |
| `flagship` | Top general capability; long-context planning. |
| `workhorse` | Solid mid-tier; quality/speed balance. |
| `fast` | Very fast, cheap; chat, summaries, formatting. |

Each mode declares a primary class plus fallbacks:

| Mode | Primary | Fallbacks |
|---|---|---|
| boss | `flagship` | `reasoner`, `workhorse` |
| chat | `fast` | `workhorse`, `flagship` |
| code | `coder` | `flagship`, `reasoner` |
| debug | `reasoner` | `flagship`, `coder` |
| hermes | `workhorse` | `fast`, `flagship` |

`va --models` resolves `model_combo.txt` → class → concrete model.

### The three layers

This distinction matters for everything below:

1. **The architecture** — modes, rules, `.ai/` contract. Pure markdown. Runs in
   Roo Code. **Language-agnostic.**
2. **The tooling** — `create-vibe-assembly`, `va` CLI, templates. JavaScript.
3. **Mission Control** — the dashboard that *watches* layer 1.

Layer 1 is what makes Vibe Assembly work. It has not changed and is not
expected to.

## Part 2 — What was done in this session

### 2.1 A CI failure that had been there since day one

**Finding.** Both CI jobs had been failing since v1.1.0 — but the full suite
takes 34 seconds locally and each CI job took **9 seconds total** including
setup. CI never reached the tests.

**Root cause.** `tests/pre-commit-hook.test.js` runs a real `git commit` in a
temp repo. CI runners have no global `user.name`/`user.email`, so it aborted with
*"Please tell me who you are."* It passed locally because your machine has a
git identity.

**Fix.** Configure the identity repo-locally in the `before()` hook, so the test
never depends on ambient git config. Verified by running with `HOME` and all
`GIT_*` identity variables stripped: 10/10 pass.

**Note on method.** The GitHub Actions log host was unreachable from this
machine (TLS handshake timeouts, then connection refused). I could not read the
failure output. I worked around it by pushing a temporary workflow that committed
its own test output back into the repo, which is readable. That workflow has
since been removed.

### 2.2 Line-ending normalization

Added `.gitattributes`. A Windows checkout was rewriting LF → CRLF, giving
`.githooks/pre-commit` a `\r` on its shebang line and making git print
*"LF will be replaced by CRLF"* on every add. Text files are now pinned to LF in
the index, and shell scripts/hooks are forced LF. Verified the hook stays
`100755` and all tests pass.

### 2.3 A Rust parser parity guard

The native parser and the JS parser both decide where Code resumes and whether
the workspace is coherent. If they ever disagree, the `va` CLI and Mission
Control tell the user different truths.

`tests/parser-parity.test.js` (87 lines) asserts the shared semantics from the JS
side: the step-prefix trap (`"step 12"` must not verify step 1), same-note
evidence (no cross-note leakage), and `none` being a real pointer rather than a
missing one. Wired into `npm test`. **77/77 JS tests pass.**

#### Why GPUI, and not a Zed fork

I researched this properly rather than assuming. Two findings settled it:

1. **Zed's extension API cannot build a dashboard.** Extensions are Rust→Wasm
   with exactly six capabilities — languages, debuggers, themes, icon themes,
   snippets, MCP servers. The `Extension` trait has no custom-UI hook; it cannot
   even register a plain command. ([docs](https://github.com/zed-industries/zed/blob/main/docs/src/extensions/developing-extensions.md))
2. **`gpui` is published standalone** (crates.io v0.2.2, Apache-2.0) and ships
   its own Windows backend. So we get Zed's rendering, windowing, and text stack
   without forking ~250 crates of editor, LSP, collab, and telemetry.

Note: `gpui_platform` is *not* published, and Zed's workspace sets
`publish = false`. The research initially recommended published `gpui`, which
would not have worked. I verified by downloading the crate and inspecting it —
published `gpui 0.2.2` has the Windows backend inline (`windows`,
`windows-core`, `embed-resource`, `src/platform/windows/`) with no dependency on
`gpui_platform`.

#### Design rules, in priority order

1. **Answer "what do I do next?" within five seconds.** The NEXT ACTION band is
   the only large element on screen and is always at the top.
2. **A contract violation must be impossible to miss.** It takes over that band.
3. **Everything else earns its space.**

The old Electron UI violated rule 3 — four raw-markdown panels competed for
equal weight with the one thing that mattered.

#### Three real bugs the old UI had

Found by reading the old renderer, not by taste:

- **KNOWN BUGS was broken.** `renderBugs` did `Object.entries(f).slice(0,6)` on
  `parseStateFile` output, rendering *one bug's field labels* (Date, Symptom,
  Root cause, …) as if they were six separate bugs. With 3 bugs it showed bug 1's
  internals and nothing of bugs 2–3. The new app parses entries properly.
- **`decisions_head` was fetched and never rendered.** Dead payload; 8 ADRs
  existed and the UI showed none.
- **The resume point was never surfaced.** It is the payload of the entire relay
  system and the single most decision-relevant number in the dataset.

#### Two bugs in my own Rust port, caught by tests

- **`parse_verify` split on the wrong backtick pair**, so *no step ever captured
  its `Verify:` command* and the resume point could never be shown. This was the
  central feature.
- **`files_allowed` collected every Meta bullet**, absorbing `status`, `effort`,
  and `depends_on` instead of only the list under its own key.

Both were found by tests before the app was ever run. Neither existed in the JS.

#### Two more bugs found by running it

- **`Blockers: None.` read as a real blocker** — the template writes a trailing
  period, so the headline said BLOCKED on a healthy workspace. Fixed with
  punctuation-stripping comparison + regression test.
- **Panel `overflow_hidden` clipped wrapped rows**, cutting the known-bug symptom
  mid-sentence.

#### The Windows build problem

`cargo build` aborted with `STATUS_STACK_BUFFER_OVERRUN` (`0xc0000409`) compiling
`windows` 0.61, `ash`, `rustls`, and `gpui_http_client`.

- `RUST_MIN_STACK` **does not work** — the overflow is in the compiler's main
  codegen stack, not a worker thread.
- `-C link-arg=/STACK:...` does not work — nothing is being linked yet.
- **`ulimit -s unlimited` before invoking cargo does work.**
- Building in **debug** rather than release also helps, and dropping gpui's
  default `wayland`/`x11` features shrinks the graph (and is correct on Windows
  anyway — Win32 + DirectWrite need no features).

Documented in the README and saved to memory, because it will otherwise be
rediscovered painfully.

## Part 3 — The bigger picture: Vibe Router

### What it is

You are building **Vibe Router** — a proxy in the spirit of 9router, open for
anyone to use, running on your VPS.

```
jev  (API keys)   ┐
                  ├─→ scrape free AI providers every 6h
laya (local model)┘         │
                            ▼
              an API model (Gemini-class) organizes them
                            │
                            ▼
                     Vibe Router
              combos: every free provider's model,
              with fallback / round-robin
                            │
                  users run Vibe Router locally
```

### Why this is a good product

Routing itself is a commodity — fallback, round-robin, and retry are
straightforward and everyone has them. **The differentiator is knowing what
*class* each model is**, and that already exists in `model_knowledge.json`:
5 classes, 14 models with aliases and context limits, per-mode requirements.

A generic router hands you a list of model names.
**Vibe Router hands Vibe Assembly a reason to pick `code` → `coder` → the
strongest coder that is actually live right now.**

jev and laya are not just scraping — they are the freshness mechanism. The
curated file is a seed; jev and laya keep the truth current every 6 hours.

### Recommendation 1 — Settle the API contract before writing the router

Vibe Assembly is finished. Vibe Router is mid-build. **That means the router
gets to define the interface** — and once other people's tools depend on it,
changing it becomes painful.

If the contract is right first, Vibe Assembly never has to change again.

### Recommendation 2 — be OpenAI-compatible at the transport layer

This is what turns "for you" into "for everyone." If Vibe Router speaks standard
`/v1/chat/completions` and `/v1/models`, then every existing tool works against
it immediately — Roo Code, Cline, Cursor, anything — with no client code.

If it's a bespoke protocol, you're asking every future user to write code before
their first prompt.

Then add **one** Vibe-specific addition on top:

```
GET  /v1/models          → standard: id, owned_by
GET  /v1/assignment      → Vibe-specific: class, strengths, freshness, health
POST /v1/chat/completions → standard, with combo fallback
```

`/v1/assignment` is the thing generic routers do not have.

Vibe Assembly should prefer `/v1/assignment` and fall back to
`model_knowledge.json` when the router is unreachable — that preserves the
free, offline-capable promise. The dashboard must never hard-depend on your VPS.

### Recommendation 3 — the single-writer assumption is the biggest latent risk

You mentioned that several chats can work on one project at once, and that a
user can talk to AI mid-work.

**The ticket contract assumes a single writer.** Two modes reading and writing
the same `active_task.md` will corrupt the pointer. `validateContract` will fail
closed — good, it prevents silent damage — but the user still loses work.

This is a genuine design gap, not a bug. Options, in order of preference:

1. **Per-mode worktrees.** Each mode gets its own git worktree; the `.ai/`
   contract becomes the merge point. Cleanest, and git already solves conflict
   semantics.
2. **A lockfile on the active pointer.** Cheap, but serializes work — it defeats
   the purpose of concurrency.
3. **Last-writer-wins with a warning.** Acceptable only if the pointer is small
   and the user is told.

I'd solve this **before** concurrency is load-bearing, not after.

### Recommendation 4 — the curated file should be a seed, not the source of truth

`model_knowledge.json` is hand-curated and will go stale. Once jev and laya
report live providers, the router's `/v1/assignment` should win, with the
curated file as offline fallback. Consider adding a `refreshed` timestamp so
staleness is visible rather than silent.

### Recommendation 5 — the native app is now a network client, not an ornament

When I first proposed Rust for the dashboard, I justified it as "the dashboard
is peripheral, so Rust is unnecessary weight." **That justification was wrong.**

Mission Control is a client for your router, in an already-Rust stack. The
instinct was right; the reasoning was not. This is worth stating plainly so the
rationale is not repeated when someone asks why the GUI is Rust.

### Recommendation 6 — decide the Electron app's fate

`app/desktop/` is now redundant. It is fully recoverable from git history, so
this is safe whenever you want it. Keeping both costs 448 MB on disk and two
implementations of the same parser to keep in sync.

### Recommendation 7 — gitignore `model_combo.txt`

Verified during this handoff: `.ai/model_combo.txt` is **not** in `.gitignore`.
That file will hold your provider and router specifics, which are
machine-local. Add `model_combo.txt` while keeping
`model_combo.example.txt` tracked, so the shape stays discoverable but the
contents stay local.

## Part 4 — Recommended next steps

**Immediate (Vibe Router):**

1. Write the API contract as a spec — endpoints, request/response shapes with
   worked examples from the real `model_knowledge.json`, fallback rules, failure
   modes. This is the one thing that cannot be built later without rework, and
   it is useful whether or not Claude writes it.
2. Implement `/v1/assignment` first. It is small, and it is the moat.
3. Make `/v1/chat/completions` and `/v1/models` OpenAI-compatible.

**Short term (Vibe Assembly):**

4. Point the Rust app at `/v1/assignment` with offline fallback.
5. Decide the concurrency story (recommendation 3).

**Housekeeping:**

6. Delete or archive `app/desktop/` (Electron) — fully recoverable from git.
7. Port `va` CLI to Rust *only if* you want the whole tree in one language. The
   parser is already in Rust and parity-tested, so it is mechanical — but it is
   optional, not required. The architecture in layer 1 does not care.

**Not recommended:**

- Forking Zed. Its extension API cannot host a dashboard, and you would inherit
  ~250 crates of editor to render a read-only status view.
- Release-mode Rust builds on this machine until the stack issue is properly
  solved — debug builds work reliably.
